ResumeLens: Screening Résumés with Formal Languages

Flux — Juan Manuel Diaz Moreno · Computación y Estructuras Discretas III, 2026-2

A résumé goes in as plain text. Four formal models decide which professional profiles its explicit qualifications satisfy.

Problem

Résumés describe the same skill in many ways: JS, Javascript, JavaScript. Checking a résumé against a profile means first deciding which strings mean the same thing.

ResumeLens does not rank candidates or make hiring decisions. It only checks whether the listed qualifications match a formally defined pattern.

Approach

Each stage uses one formal model. Its output is the next stage's input.

1 Extractregular expressions
→
2 Normalizefinite-state transducers
→
3 Classifyfinite automata (DFA)
→
4 Describecontext-free grammar (textX)

Four profiles: Full Stack Developer and Machine Learning Engineer (assignment), DevOps Engineer and Data Engineer (team).

Example: Wednesday Addams

Raw (stage 1): JS, React.js, NodeJS, Postgres, Git

Normalized (stage 2):

JAVASCRIPT, REACT, NODE_JS, POSTGRESQL, GIT

Classified (stage 3): Full Stack Developer — ACCEPTED

Profile (stage 4): a validated candidate description and an HTML page.

Design decisions

  • Transducers read whole tokens, not characters.
  • Stage 2 sorts terms by profile, so stage 3 never has to guess which slot a term fills. This makes the automata deterministic (DFA).
  • Optional qualifications don't reject a candidate.
  • Any recognized database term fills the database slot.

Validation

  • 99 automated tests across the four stages and the command line.
  • The grammar rejects lexical errors (e.g. lowercase skill), syntax errors (e.g. missing skills section), and out-of-vocabulary skills (e.g. COBOL).

Limitations and future work

  • Extraction assumes the name is on the first line.
  • Language names are case-sensitive, to avoid matching the word "go".
  • Only ten hand-written résumés were tested.
  • Adding a new term means changing the regex and the transducer.
